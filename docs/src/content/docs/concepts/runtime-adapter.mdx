The **RuntimeAdapter** is the one place in Hostwright that talks to the runtime.
Every other module, including the reconciler, the CLI, and the state store,
reaches the runtime through this boundary. This single boundary is the most important
architectural decision in the project.

![Hostwright core talks only through the RuntimeAdapter interface to a CLI adapter today and a planned native adapter later.](/diagrams/06-runtime-adapter-boundary.svg)

## Why a single boundary

Apple container is young and evolving. Its command surface, structured output,
and native APIs will change. If assumptions about it were scattered across the
reconciler, the state store, and the CLI, every runtime change would ripple
through the whole codebase.

By forcing every runtime operation through one typed protocol, Hostwright keeps
those assumptions contained. The reconciler works against an abstract contract;
it does not know or care whether the call is served by shelling out to the
Apple container CLI or by a future Swift-native client.

## The contract

The adapter exposes:

- `metadata()`: adapter and runtime identity;
- `capabilities()`: supported capability discovery;
- `observe(desiredState:)`: read-only runtime snapshots;
- `plan(desiredState:observedState:)`: adapter-aware planning hooks;
- `logs(for:tail:)`: bounded read-only log output;
- `execute(_:confirmation:)`: the mutation hook. It may perform exactly one
  supported mutation action, and only after confirmation, plan hash, policy
  validation, and state persistence gates have all passed.

Typed inputs, typed outputs, typed errors. The reconciler never parses a
human-readable table.

## Command classification

Every process the adapter might run is represented as a typed command spec and
classified as `readOnly`, `mutating`, `forbidden`, or `unknown`. The process
runner is not a general shell-out path:

- the executable must resolve through a controlled resolver;
- read-only commands must pass read-only policy;
- mutating commands must carry one of a bounded set of supported kinds:
  lifecycle actions (create, start, stop, restart, remove, update a managed
  service), image actions (pull, push, tag, load, save, build, delete), and
  interactive actions (exec, attach, copy, export), each gated behind its own
  confirmation and capability check;
- forbidden, unknown, and unsupported specs are rejected before execution;
- every command has a timeout (default 30 s, maximum 300 s) and captured,
  **redacted** output.

Redaction applies to command arguments, environment values, stdout, stderr,
parser errors, and runtime error messages. Sensitive key fragments such as
`token`, `password`, `secret`, `credential`, `auth`, and `key` are masked.

## Identity and ownership

Hostwright-created resources carry collision-resistant versioned runtime
identifiers and exact ownership labels. Observation binds current-project
labels to the exact identifier, keeps owned orphans visible, ignores unrelated
labeled projects, and fails closed on malformed current-project ownership.
Managed start, managed restart, and cleanup operate on **exact identifiers
only**. Exact-identifier targeting lets two projects with identical legacy
names remain distinct and safely cleanable.

## Fail-closed parsing

The observation parser accepts only reviewed shapes: the fixture-defined
observation schema, the verified real empty `container list --all --format
json` output, Apple builder output (ignored as non-Hostwright state), and exact
labeled Apple container 1.0.0 rows with network metadata (hostname, IPv4/IPv6,
gateway, MAC, network name, MTU). Anything else is reported as a parse
failure; unverified CLI output is never converted into observed state.

<Aside type="note" title="Adapter scope">
Apple container owns its internals: helpers, VM lifecycle, and the networking
stack. The adapter's reviewed surface now covers the full lifecycle, image,
and interactive command families documented in the [CLI
reference](/reference/cli/); it still rejects anything outside that reviewed
surface, including custom networks, DNS, and broad flags like `--all` or
`--force`. See the [Apple container boundary](/concepts/apple-container-boundary/).
</Aside>

## Two providers today

Two runtime providers implement the adapter contract: the **Apple CLI**
provider (`--runtime-provider apple-cli`, stable ID `apple-container-cli`),
which drives the Apple `container` CLI for both observation and mutation, and
the **Containerization** provider (`--runtime-provider containerization`,
stable ID `apple-containerization`), which drives the pinned Containerization
framework through an authenticated out-of-process helper,
`hostwright-containerization-helper`. Both are negotiated through
`hostwright runtime providers` and pass the same capability conformance suite
for every feature they declare; the Containerization provider currently
exposes a smaller local-image-only subset for image mutation. A project binds
to one provider at a time, and moving between them goes through the fenced
[`hostwright runtime migrate`](/reference/cli/#hostwright-runtime-migrate)
operation, never a silent switch.
